# 놀이 데이터 임포트 스킬

정규화된 JSON 파일을 `data/plays.json`에 초안으로 병합하고 로컬 서버 검수를 준비합니다. 기본 흐름은 수집 → 정규화 → `draft` 병합·ID 부여 → 놀이 대표 이미지·없는 새 재료 이미지 자동 생성·저장 → 새 검수 배치 등록 → **서버 검수 링크 전달** → 사용자가 승인한 항목만 로컬 반영입니다. 임포트는 게시 승인이 아닙니다. 검수 준비 시 [공통 서버 인계 절차](../../../tools/local-review/README.md#수집-스킬에서-검수로-넘기기)를 읽고 따릅니다.

**입력**: `$ARGUMENTS` (예: `results/normalized/18개월_소근육_20260401_020407_normalized.json`)

사용자의 `import-play` 표현은 이 저장소의 실제 스킬명 `import-plays`로 처리합니다. 현재 대화에서 정한 파일은 인자가 없어도 단일 대상으로 사용하며, 아래 전체 처리는 대상이 지정되지 않았을 때만 적용합니다.

---

## Step 1: 파일 읽기

### 기존 plays.json 읽기

`data/plays.json`이 있으면 Read로 읽습니다.

없으면 아래 초기 구조를 사용합니다:

```json
{
  "version": "1.0.0",
  "updatedAt": "2026-04-01",
  "importedFiles": [],
  "plays": []
}
```

### 대상 파일 결정

**`$ARGUMENTS`가 있는 경우**: 해당 파일을 단일 대상으로 처리합니다.

**`$ARGUMENTS`가 비어 있는 경우**: `results/normalized/` 디렉토리의 **전체** `_normalized.json` 파일을 처리 대상으로 합니다.

```bash
ls results/normalized/*_normalized.json
```

`plays.json`의 `importedFiles` 배열과 대조하여 **아직 처리되지 않은 파일**만 추려냅니다.

- 처리 대상이 없으면 신규 ID를 만들지 않습니다. 현재 요청에 해당하는 기존 배치가 있으면 같은 `--batch`로 화면을 갱신해 서버 검수 링크를 다시 전달하고, 없으면 전체 현황과 미처리 파일이 없음을 안내합니다.
- 처리 대상 파일 목록을 먼저 출력합니다:

```
## 처리 대상 파일 ({n}개)
1. results/normalized/18개월_소근육_20260401_020407_normalized.json
2. results/normalized/27개월_인지_20260405_103022_normalized.json
...
```

각 대상 파일을 순서대로 Read하여 처리합니다. 파일마다 Step 2~4를 완료한 뒤 다음 파일로 넘어갑니다.

## Step 2: 중복 체크

정규화 파일의 각 activity를 기존 `plays.json`의 plays와 비교합니다.

### 중복 판정 기준

아래 조건에 해당하면 중복으로 판정합니다:

1. **이름 일치 + 연령 겹침**: `name`이 완전히 동일 **AND** 연령 범위가 겹침
   - 연령 겹침: `newAgeMin <= existingAgeMax AND newAgeMax >= existingAgeMin`
2. **이름 유사 + 연령 겹침**: 공백/조사/구두점 제거 후 핵심 키워드가 동일 **AND** 연령 범위가 겹침
   - 예: "빨대 꽂기 놀이" vs "빨대꽂기 놀이" + 연령 겹침 → 중복
   - 예: "스티커 붙이기 떼기 놀이" vs "스티커 붙이기·떼기" + 연령 겹침 → 중복
   - 단, 이름이 유사하더라도 연령 범위가 **전혀 겹치지 않으면** 별개의 놀이로 취급
3. **동일 소스 + 이름 유사 + 연령 겹침**: `source.url`이 동일 **AND** 이름 유사 **AND** 연령 범위가 겹침
   - 같은 URL이라도 이름이 다르거나 연령이 다르면 별개의 놀이로 취급
   - 예: 동일 URL, "빨대 꽂기" 12-24개월 vs "빨대 컵에 꽂기" 22-30개월 → 이름 다름 → 별개

### 중복 처리

- 유사 이름과 공통 재료만으로 제외하지 않습니다. 목표·규칙·핵심 동작·결과를 함께 비교합니다. 기존 가위질과 괴물 미용실처럼 실제 역할·목표가 추가된 활동은 구분 근거를 수집 메타데이터에 남깁니다. 이름만 다르고 진행이 같은 활동은 중복입니다.
- 중복 항목은 **건너뜁니다** (기존 데이터 유지)
- 기존 `draft`·`archived` 및 `imageStatus: review`를 재임포트로 자동 해제하지 않습니다
- 중복 목록을 Step 5 요약에 표시합니다

## Step 3: ID 부여 및 스키마 변환

### ID 생성

기존 `plays.json`에서 가장 큰 ID 번호를 찾아 이어서 부여합니다.

- ID 형식: `play_001`, `play_002`, ... `play_999`
- 기존 최대 ID가 `play_015`이면 → 새 항목은 `play_016`부터 시작

### 스키마 변환

정규화 파일의 activity를 `plays.json` 스키마로 변환합니다.

**추가/변환할 필드:**
- `id`: 위에서 생성한 ID
- `createdAt`: 마스터에 처음 등록하는 한국 날짜 (`YYYY-MM-DD`). 수집일·원문 게시일 대신 실제 등록일을 사용. 기존 항목 수정·재임포트 시 최초 값을 보존하고, 날짜 없는 과거 항목에 오늘 날짜를 일괄 부여하지 않음. `NEW` 배지는 이 날짜부터 달력 기준 한 달 동안만 표시.
- `materials.substitutes`: 항상 빈 배열 `[]`
- `status`: 신규 항목은 정규화본의 값과 관계없이 `"draft"`. 사용자의 서버 UI 승인 또는 명시된 승인 결과만 기존 승인 반영 도구로 검증해 `"live"` 전환

**선택 필드 보존:**
- `tip`: 현재 스키마에 있는 선택 문자열 필드. 삭제하거나 steps에 중복 병합하지 않음
- `imageStatus`: 신규 항목은 `review`. 일치하는 그림을 준비한 뒤에도 사용자 검수 승인 전에는 해제하지 않음
- 이미지가 없는 신규 항목도 `imageStatus: review`를 기록해 기존 앱/웹의 기본 이미지 처리를 사용. 초안 ID를 먼저 부여하되 기본 전체 흐름에서는 대표 이미지 실제 생성까지 이어서 수행
- 수집·정규화의 `meta` 및 활동별 검토용 필드는 마스터의 놀이 객체에 복사하지 않음
- 신규 등록의 `steps`와 `tip`에 ‘원문’, ‘등록본’ 등 수집·편집 과정 설명이 섞여 있으면 보호자가 따라 할 동작과 실용적인 팁으로 다듬음. 검토 근거는 수집 파일에 남기고 `source`를 보존하며 재료·안전 조건은 바꾸지 않음

**유지할 필드 (그대로 복사):**
- `name`, `ageMin`, `ageMax`, `place`, `durationMin`, `durationMax`, `prepTime`
- `difficulty`, `devAreas`, `materials.required`, `materials.optional`
- `steps`, `safetyNotes`, `educationalEffects`, `tags`, `source`

### 검증

각 변환된 항목에 대해 아래를 확인합니다:

- `ageMin` <= `ageMax`
- 신규 항목의 `createdAt`이 실제로 존재하는 `YYYY-MM-DD` 날짜인지 확인
- `0 < durationMin` <= `durationMax`
- `devAreas`의 모든 값이 유효한 enum: `fine_motor`, `gross_motor`, `cognitive`, `language`, `emotional`, `social`, `sensory`
- `place`가 유효한 enum: `indoor`, `outdoor`, `any`
- `difficulty`가 1, 2, 3 중 하나
- `materials.required`와 `materials.optional`의 모든 slug가 표준 재료 마스터에 존재
- 출처 유형·URL 도메인 및 개별 원문 여부가 일치. 검색 결과를 영상 출처로 넣지 않음
- 필수와 선택은 기본형 한 가지의 실제 준비물에 맞춤. 대안 도구를 모두 필수로 합치지 않음
- 생가루, 3세 미만의 작은 구슬·공작 조각·일반 슬라임 등은 `/validate-plays`의 게시 제한을 준수

**표준 재료 slug 목록:** `data/materials.json`의 `categories` 필드를 Read하여 모든 배열을 합친 것을 유효 slug 집합으로 사용합니다.

검증 실패 항목이 있으면 사용자에게 아래 형식으로 안내합니다:

```
## 검증 오류

| # | 놀이명 | 필드 | 오류 내용 |
|---|--------|------|----------|
| 1 | 쌀 촉감 놀이 | materials.required | "rice"는 표준 slug에 없음 |
| 2 | ... | ... | ... |

- 필수 재료 문제는 항목을 draft로 보류
- 새 재료는 의미를 확인해 임시 정의와 reviewPending으로 HTML 검수 준비
- 의미·안전·방법이 보존되는 대안만 실제 검토 후 사용
```

현재 자료로 해결할 수 있는 오류는 수정하고 Step 4로 진행합니다. 재료 의미나 활동 자체를 바꾸는 판단에 사용자 정보가 필요한 경우에만 질문합니다.

## Step 4: 병합, 저장 및 검증

### 병합

기존 `plays.json`의 `plays` 배열 끝에 새 항목들을 추가합니다.

- 현재 작업 전 파일을 백업하거나 내용 해시를 기록합니다. 저장 직전에 최신 파일을 다시 읽고 변경되었으면 최신 상태를 기준으로 ID·중복을 다시 계산합니다. 다른 작업의 미커밋 변경을 덮어쓰지 않습니다.
- 이미 `importedFiles`에 있는 대상은 명시적으로 지정했더라도 재등록하지 않습니다. 파일명은 기존 형식대로 기록하되 동명 파일의 내용이 다르면 다른 배치인지 검토합니다.
- ID는 현재 최대 번호 다음부터 부여하고 1000 이상도 허용합니다. 기존 ID·createdAt·본문·tip·상태·이미지 검토 이력은 그대로 보존합니다.

### 메타데이터 갱신

```bash
date +%Y-%m-%d
```

- `updatedAt`: 오늘 날짜로 갱신
- `version`: 유지 (변경하지 않음)
- `importedFiles`: 처리 완료된 파일의 **파일명**(경로 제외)을 배열에 추가
  - 예: `"27개월_소근육_20260407_122021_normalized.json"`
  - 신규 추가가 0건이더라도(전부 중복) 처리 완료로 기록

### 디렉토리 생성 및 저장

```bash
ls data/
```

`data/` 디렉토리가 없으면:
```bash
mkdir -p data
```

Write 도구로 `data/plays.json`에 저장합니다. JSON은 2칸 들여쓰기로 포맷합니다.

### 저장 후 자동 검증

저장 완료 후 `/validate-plays` 스킬의 검증 로직을 자동 실행합니다.

- 검증 통과 → Step 5 결과 요약으로 진행
- **오류 발견 시** → 해당 항목을 추천에 포함하지 않고 원인을 수정하거나 draft로 보류. 기존 보류 이력 유지
- 기본 마스터는 `pnpm check:play-content`도 실행해 결정적 오류를 확인
- 새 재료를 추가했으면 `pnpm typecheck`와 관련 기존 테스트를 실행해 앱 연결을 확인
- 실제 이미지 확인 전에는 `review`를 유지. 웹 이미지 준비 과정이 신규 ID의 기본 이미지를 만들 수 있는지 확인하고, 이미지 개수를 기존 191개 같은 숫자로 고정하지 않음

### 놀이·재료 서버 검수 준비

1. 파일별로 실제 부여한 신규 ID를 기록하고 [generate-play-images](../generate-play-images/SKILL.md)와 [공통 이미지 절차](../../../tools/local-review/IMAGE-WORKFLOW.md)를 수행합니다. 별도 이미지 요청 없이 프롬프트 작성 → 실제 `image_gen` 호출 → 시각 확인 → `review:image` JPEG 저장까지 완료합니다. `review:images`에서 모든 신규 ID가 `ready`여야 다음 단계로 진행합니다. 실패 시 초안·완료 이미지를 보존하고 미완료 ID를 보고하며 새 배치를 만들지 않습니다.
2. [generate-material-images](../generate-material-images/SKILL.md)를 이어서 수행합니다. `review:material-images --ids <이번-ID목록>`으로 이번 놀이가 쓰는 미승인 재료만 중복 제거하고 실제 기존 그림은 재사용합니다. 이미지가 없으면 별도 요청 없이 실제 생성·시각 확인·`review:material-image` 저장·매핑까지 수행합니다. 새 재료가 모두 `ready` 또는 `existing`이어야 합니다. 실패 시 초안·완료 이미지를 보존하고 새 배치를 만들지 않습니다.
3. 해당 **정규화 파일**의 메타데이터를 연결합니다. 예시 ID나 전체 마스터의 ID를 넣지 않습니다. 원본이 `_done.json`으로 바뀌었어도 존재하는 정규화 파일 경로를 사용합니다.

   `pnpm review:prepare --ids <실제-신규-ID목록> --source <정규화-파일> --title <수집-제목>`

4. 반환된 `batchPath`·`batchId`·`review`를 보존합니다. 수정·재실행에는 `pnpm review:prepare --batch <배치-경로>`를 사용합니다. 실제 새 재료 제안은 기존 배치에 필요한 만큼 보완하고, `appliedMaterialDecisions`·`entries.materialReplacementChecks`와 기존 의견은 보존합니다. 신규 ID가 0개면 빈 배치를 만들지 않고 기존 해당 배치나 현황을 안내합니다.
5. 놀이 대표 이미지는 색연필·수채화/크림 배경, 새 재료는 흰 배경의 부드러운 3D 스타일을 유지합니다. 두 종류 모두 준비된 실제 파일을 검수 화면에 연결합니다.
6. 이 저장소의 서버가 실행 중이면 재사용하고, 없으면 루트에서 `pnpm review:local`을 실행합니다. 공통 절차대로 API에서 해당 배치의 ID·내용을 대조하고 실제 검수 URL을 확인해 **수집 건별 서버 검수 링크와 전체 현황 링크**를 전달합니다. 다른 포트로 실행했다면 확인한 그 주소를 사용합니다. 기존 화면은 최신 파일로 새로고침합니다.
7. 새 놀이의 `draft`·`imageStatus: review`, 신규 재료의 `reviewPending`과 대표 이미지 완료 수를 확인해 사용자 검수 대기로 보고합니다. 서버 연결이 불가능하면 확인한 정적 HTML을 대안으로 전달하고, 서버 저장·즉시 반영이 연결되지 않았음을 설명합니다.

### 사용자 승인과 수정 후 재검수

- 서버 화면의 의견·확인란·상태는 `results/local-review/state.json`에 자동 저장됩니다. 사용자의 **승인 버튼**이 해당 놀이만 기존 검증 모듈로 검증해 `live`·이미지 매핑에 반영하므로 별도 JSON 내보내기·CLI 재반영을 요구하지 않습니다. 검수 준비 중 확인란·승인 버튼을 대신 조작하거나 승인 값을 만들어 게시하지 않습니다. 사용자 승인이 이미 명시된 경우에는 해당 범위만 현재 내용·이미지와 대조해 기존 도구로 처리합니다.
- 신규 재료는 같은 화면의 재료 탭에서 먼저 **신규 추가·대체·보류**를 반영합니다. 미승인·보류 재료를 쓰는 놀이는 승인할 수 없습니다. 대체 후 방법·준비 조건·주의사항을 실제로 고치고 이미지도 다시 확인한 뒤 놀이를 재검수합니다.
- 수정 요청은 사용자가 남긴 의견을 확인해 실제 본문·재료·이미지를 보완합니다. 같은 배치로 `review:prepare --batch ...`를 실행하고 서버에서 새로고침합니다. 보류·수정 요청은 초안을 유지하며 과거 해시의 승인을 새 내용에 재사용하지 않습니다.
- 이미 등록된 놀이는 “등록 완료”로 표시합니다. 새 JSON에 미검수로 들어 있어도 기존 승인을 취소하지 않으며 다시 승인하도록 요구하지 않습니다.
- `409` 충돌이면 현재 의견을 보관하고 최신 파일을 다시 읽어 검수하며, `423`은 공통 문서의 복구 절차를 따릅니다. 승인 요청의 버전만 바꿔 재전송하거나 서버 상태·거래·영수증을 직접 편집하지 않습니다.
- `file://`/JSON 방식도 유지합니다. 서버로 JSON을 가져오면 기록만 저장되며 등록은 각 항목의 승인 버튼으로 처리합니다. 사용자가 JSON/CLI 반영을 요청했다면 같은 `--batch`로 재료 `review:materials`를 먼저 미리보기·`--write` 적용하고, 변경 후 새 화면에서 재검수한 최신 놀이 결과만 `review:apply` 미리보기·`--write`로 반영합니다.
- 반영 후 콘텐츠·타입·이미지 검증을 실행하고 필요한 정적 HTML을 같은 배치로 갱신합니다. 서버 화면은 반영 후 자동 갱신되며, 다른 열린 화면은 새로고침합니다. 배포는 별도 요청이 있을 때 진행합니다.

## 에러 처리

### 입력 오류
- 파일이 존재하지 않거나 `_normalized.json`이 아닌 경우:
  ```
  해당 파일을 찾을 수 없거나 정규화된 파일이 아닙니다.
  사용법: /import-plays results/normalized/{파일명}_normalized.json
  ```

- `results/normalized/` 디렉토리에 파일이 없는 경우:
  ```
  정규화된 파일이 없습니다.
  먼저 /normalize-materials를 실행하여 재료를 표준화해주세요.
  ```

- 전체 처리 시 미처리 파일이 없는 경우:
  ```
  모든 파일이 이미 임포트되었습니다. (importedFiles: {n}개)
  새로 정규화된 파일이 있으면 /normalize-materials를 먼저 실행하세요.
  ```

### 데이터 오류
- 정규화 파일에 `activities` 배열이 없거나 비어있는 경우:
  ```
  정규화 파일에 놀이 데이터가 없습니다.
  파일을 확인해주세요: {파일 경로}
  ```
