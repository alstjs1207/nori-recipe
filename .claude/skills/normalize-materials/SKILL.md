# 재료 표준화 스킬

play-recipe로 추출한 JSON 파일의 재료를 표준 재료 목록으로 변환합니다. 신규 놀이와 재료는 검수 대기로 준비하고, 활성 등록은 사용자 승인 후 기존 반영 도구가 처리합니다. 전체 수집·검수 요청의 한 단계라면 [공통 서버 인계 절차](../../../tools/local-review/README.md#수집-스킬에서-검수로-넘기기)에 따라 임포트·놀이 및 새 재료 이미지 실제 생성·검수 연결까지 이어갑니다. 정규화만 요청한 경우에는 정규화 산출물과 다음 단계 안내까지 완료합니다.

---

## Step 0: 대상 파일 선택

`$ARGUMENTS`, 사용자 메시지의 파일 경로 또는 현재 대화에서 선정한 후보의 수집 파일이 있으면 그 파일을 바로 처리합니다. 이미 정한 대상을 다시 선택하게 하지 않습니다. 후보 목록 전용 JSON은 먼저 play-recipe의 `meta` + `activities` 수집 구조로 변환합니다.

대상이 정해지지 않은 경우에만 아래 목록을 조회합니다. 후보가 하나면 바로 사용하고, 여러 파일 중 대상을 추론할 수 없으면 파일 선택을 요청합니다.

`results/` 디렉토리에서 정규화 대상 후보 파일을 조회합니다.

```bash
ls -t results/*.json
```

**`_normalized.json` 또는 `_done.json`으로 끝나는 파일은 후보에서 제외**합니다 (이미 처리된 파일).

- 놀이 수는 각 파일을 Read로 읽어 activities 배열 길이를 확인합니다.
- 후보가 0개이면 "정규화할 파일이 없습니다."를 출력하고 종료합니다.
- 후보가 여러 개이고 대상을 알 수 없으면 현재 환경의 질문 도구로 파일 선택을 요청합니다. `AskUserQuestion`이 없는 환경에서는 그 도구 이름을 전제하지 않습니다.

**AskUserQuestion 호출 형식**:

```
question: "어떤 파일을 재료 표준화할까요?"
header: "파일 선택"
multiSelect: true
options: (후보 파일별로 최대 4개, 파일이 4개 초과 시 최신 4개만 표시)
  - label: "18개월_소근육_20260330_141344.json"
    description: "놀이 15개"
  - label: "18개월_소근육_20260330_143954.json"
    description: "놀이 12개"
```

사용자가 선택한 파일을 대상으로 Step 1부터 진행합니다. 여러 파일 선택 시 순차 처리합니다.

---

## 표준 재료 목록

`data/materials.json`이 단일 소스입니다. 스킬 시작 시 Read로 읽어 slug 목록과 displayNames를 사용합니다.

```
Read: data/materials.json
```

- 유효 slug 목록: `categories` 필드의 모든 배열을 합친 것
- 한글 표시명: `displayNames` 필드
- 제거된 slug: `removed` 필드 (매핑 시 참고)

## 처리 규칙

### Step 1: 파일 읽기

Step 0에서 사용자가 선택한 파일을 Read로 읽습니다.

### Step 2: 재료 매핑

`data/materials.json`의 실제 key로 매핑합니다. 이름이 비슷하다는 이유만으로 재료의 기능·크기·식용 여부를 바꾸지 않습니다.

- 빨대 → `straw`, 집게 → `tongs`, 플레이콘 → `play_corn`은 현재 등록된 slug입니다. 오래된 예시를 기준으로 삭제하지 않습니다.
- 두부·플레인 요거트·불린 미역은 해당 활동의 실제 식재료가 맞으면 `soft_food`로 표현할 수 있습니다. 본문에는 구체적인 종류와 준비 상태를 유지합니다.
- 두부→클레이, 요거트/미역→슬라임, 쌀알/빵가루→쌀가루/생밀가루, 튀밥/커피→모래는 직접 매핑이 아닙니다. 영아 재료로 바꾸어 추천하지 않습니다.
- 일반 공과 대형 운동공, 평평한 매트와 등반 교구, 비즈와 구멍 없는 구슬, 스펀지와 쿠션은 목적·구조가 다릅니다. 실제 활동 조건을 따로 확인합니다.
- 수량은 slug 배열에서 빼되 본문에 필요한 수량·크기·제품 사용 연령·보호자 준비 조건을 유지합니다.
- 안전 가위→`scissors`, 종이/신문지→`paper`, 컵→`cup`, 그릇→`bowl`, 천→`cloth` 등 실제 의미가 일치하는 재료만 변환합니다.
- 종이컵은 `paper_cup`, 투명 플라스틱 컵은 `transparent_cup`입니다. 놀이에 필요한 종이 재질·투명성을 일반 `cup`으로 없애지 않습니다.
- `crayon`의 표시명은 크레용·색연필입니다. 원문 마커·페인트 스틱을 색연필로 쓰는 편집 응용은 방법과 검토 기록에 명시한 뒤 매핑합니다. 원문에 색연필이 있었다고 기록하지 않습니다.
- 액체풀과 약한 점착 종이테이프는 각각 `glue`·`tape`로 묶되 필요한 제품 형태를 본문에 유지합니다. 소금·폼폼·훌라후프·붓·종이접시·동물 피규어·키친타월은 마스터의 해당 slug를 읽어 사용하며 밀가루·스펀지·공·고체풀·인형 등으로 임의 치환하지 않습니다.

### Step 3: 결과 구조 변환

영문 slug를 사용하며 `required`, `optional`, `substitutes`를 모두 기록합니다. `substitutes`는 항상 `[]`입니다.

```json
"materials": {
  "required": ["straw", "cup", "cardboard", "tape"],
  "optional": [],
  "substitutes": []
}
```

위 예시는 보호자가 구멍 있는 골판지 뚜껑을 미리 만들어 컵에 붙인 뒤 빨대를 꽂는 **실제 장치 준비 단계가 본문에 있을 때**만 유효합니다. 일반 컵을 구멍 뚫린 소쿠리로 취급하지 않습니다.

- 한 가지 기본형에 꼭 필요한 재료만 `required`에 넣습니다.
- 집게/숟가락, 종이/책, 블록/컵 등 대안을 동시에 필수로 묶지 않습니다. 기본형 한 가지를 선택하고 다른 변형은 선택 재료와 별도 방법으로 설명합니다.
- 중복 slug와 required/optional 중첩을 제거합니다.
- 도구 없이 가능한 기본형은 `required: []`가 맞을 수 있습니다. 고정 가구·목욕 등 필요한 환경은 본문에 명시합니다.
- 필수 재료가 미해결인 활동은 실행 가능한 재료 없는 놀이로 바꾸지 않습니다. 원본과 미매핑 사유를 보존하고 `status: draft`로 보류합니다. 배열에 빈 문자열을 저장하지 않습니다.

### Step 3.5: 미매핑 재료 처리

1. 사용자에게 이미 재료 등록·수정·보류에 대한 지시를 받았는지 먼저 확인합니다. 현재 지시로 해결 가능한 교정은 진행합니다.
2. 기본 로컬 서버 검수 흐름에서는 선정한 놀이의 실제 신규 재료를 의미가 맞는 slug·표시명·카테고리로 정의하고 `reviewPending`에 넣습니다. 이는 검수용 임시 정의이며 정규화 완료만으로 활성화하거나 `reviewPending`을 해제하지 않습니다. 승인된 기존 재료는 그대로 재사용하며 검수 대기로 되돌리지 않습니다. 이미 명시된 사용자 승인은 해당 범위만 기존 검증·반영 도구로 처리합니다. 재료의 의미를 확인할 수 없거나 활동 자체를 바꾸는 대체가 필요할 때만 묶어서 질문합니다.
   - 카테고리·표시명의 단일 소스는 `data/materials.json`입니다. 새 slug의 앱 타입, 재료 이미지와 웹 출력 연결도 확인합니다. 초안 단계에서는 브랜드 기본 이미지를 사용할 수 있지만, 전체 흐름의 검수 인계 전에는 [generate-material-images](../generate-material-images/SKILL.md)로 실제 이미지를 생성·저장·연결합니다. 실제 기존 이미지는 재사용하고 다른 재료 사진으로 대신하지 않습니다. 정규화만 요청했다면 이미지 생성까지 확장하지 않습니다.
3. 검수할 신규 재료를 **정규화 파일**의 `meta.materialProposals`에 기록합니다. 원본의 제안·검토 근거가 있으면 보존·보완합니다. 항목은 `slug`, `originalNames`(배열), `purpose`, `reason`, `similar`(실제로 대체 가능한 승인된 기존 slug 배열)을 포함합니다. 이 파일을 임포트와 `review:prepare --source`에 넘겨 실제 사용 재료만 검수 화면에 연결합니다. 의미가 다른 기존 slug로 임의 치환하지 않습니다.
4. 대안 재료가 있는 경우에도 다음 단계의 검토를 통과해야 합니다. 단순한 유사 재료 추천을 정답으로 삼지 않습니다.

예: 쌀알은 `rice_flour`와 다릅니다. 쌀알의 임시 정의와 등록 제안을 검수 화면에 넣을 수 있지만 사용자 승인 전에는 색깔쌀 활동을 추천에 넣지 않습니다.

### Step 3.6: 재료와 전체 내용 검토

정규화한 모든 활동을 아래 순서로 검토합니다. 사용자에게 같은 내용을 세 번 반복할 필요는 없으며 변경 사유는 결과 로그에 남깁니다.

1. **의미 확인**: 원본의 식품/공작 재료, 알갱이/가루, 구멍/뚜껑 구조, 도구 기능이 보존되는지 확인합니다.
2. **안전·준비 확인**: 월령·제품 연령·입 탐색·작은 부품·알레르기·실제 설치 조건을 검토합니다. 생밀가루·생반죽 직접 놀이는 live로 만들지 않습니다. 작은 구슬·비즈·워터비즈·플레이콘·일반 슬라임은 3세 미만 추천에서 제외합니다.
3. **전체 내용 확인**: 이름·재료·단계·팁·효과·태그·출처·그림이 같은 활동을 설명하는지 읽습니다. 사용하지 않는 도구나 삭제한 동작·치료 효능을 효과/태그에 남기지 않습니다.

원본과 다른 수동 활동으로 재작성했다면 검증하지 않은 원문에 그 방법을 귀속하지 않습니다. 원본 정보는 수집 파일에 보존하고 출처는 `manual`로 정리합니다. 기존 그림이 새 내용과 어긋나면 `imageStatus: review`를 기록합니다.

확실히 수정할 수 없는 필수 조건은 draft로 보류합니다. 재료·방법·연령·출처 검토를 해결해도 신규 활동은 사용자 검수 승인 전까지 draft를 유지합니다. 기존 마스터의 draft·archived도 자동 해제하지 않습니다. 저장 전 `/validate-plays`의 규칙을 적용합니다.

본문과 일치하는 이미지가 아직 없는 신규 활동에는 `imageStatus: review`를 추가합니다. 등록을 위해 다른 놀이 그림을 연결하거나 원문 이미지를 무단 복사하지 않습니다.

### Step 4: 저장

정규화 파일 저장과 원본 완료 표시를 수행합니다. 재료 마스터를 보완할 때는 최신 파일을 다시 읽어 기존 표시명·카테고리·`reviewPending`과 승인 이력을 보존합니다. 저장 직전 파일이 바뀌었으면 최신 상태에서 매핑을 다시 확인하며, 이전 사본으로 덮어쓰지 않습니다. 서버의 검수 상태·거래 파일은 직접 수정하지 않습니다.

#### 4-1. 결과 파일 저장

변환된 JSON을 `results/normalized/` 디렉토리에 `_normalized` 접미사를 붙여 저장합니다.

**파일 경로**: 원본이 `results/18개월_소근육_20260330_143954.json`이면
→ `results/normalized/18개월_소근육_20260330_143954_normalized.json`

`results/normalized/` 디렉토리가 없으면 생성합니다.

meta 정보에 아래 필드를 추가합니다:
```json
"normalization": {
  "normalized_at": "2026-03-30T15:00:00",
  "original_file": "18개월_소근육_20260330_143954.json",
  "original_activity_count": 15,
  "normalized_activity_count": 13,
  "removed_activities": ["과자 집기 놀이"],
  "user_mapped": {
    "두부": "soft_food"
  }
}
```

기존 `meta.activityReviews`와 `meta.materialProposals`는 보존합니다. 실제 원문 재료 → slug 매핑, 신규 slug의 검수 대기 여부와 승인 근거, 응용 변경, 보류 이유를 `normalization`에 기록합니다. 확인을 받지 않은 매핑을 `user_mapped`라고 쓰지 않습니다.

#### 4-2. 원본 파일 완료 표시

원본 파일명에 `_done`을 붙여 리네임합니다.

```bash
mv results/18개월_소근육_20260330_143954.json results/18개월_소근육_20260330_143954_done.json
```

이렇게 하면 Step 0에서 `_done.json`으로 끝나는 파일도 후보에서 자동 제외됩니다.

`_done`은 정규화 처리 완료 표시이며 사용자 검수·재료 승인·놀이 등록 완료를 뜻하지 않습니다. 후속 단계에는 이름이 바뀐 원본의 옛 경로 대신 실제 저장한 정규화 파일 경로를 전달합니다.

#### 4-3. 임포트와 서버 검수로 연결

- 전체 수집·검수 흐름이면 [import-plays](../import-plays/SKILL.md)에 방금 저장한 정규화 파일을 명시해 초안으로 병합합니다. 정규화만 요청했다면 이 파일 경로와 신규 재료 제안·미해결 사유를 전달하고 마칩니다.
- 임포트에서 부여한 실제 신규 ID를 [generate-play-images](../generate-play-images/SKILL.md)에 넘겨 프롬프트 작성부터 실제 생성·JPEG 저장까지 이어갑니다. [공통 이미지 절차](../../../tools/local-review/IMAGE-WORKFLOW.md)의 `review:images`에서 모든 대표 이미지가 `ready`가 된 뒤 배치를 준비합니다. 실패하면 초안·완료 이미지를 보존하고 미완료 ID를 보고하며 새 배치는 만들지 않습니다. 이미 해당 수집 건의 배치가 있으면 같은 경로를 재사용하며 신규 재료 제안만 필요한 만큼 보완합니다. 기존 `appliedMaterialDecisions`와 대체 후 재검수 정보는 보존합니다.
- 놀이 대표 이미지 뒤 [generate-material-images](../generate-material-images/SKILL.md)를 이어서 수행해 이번 놀이에 필요한 새 재료의 없는 이미지를 생성합니다. `review:material-images --ids ...`에서 새 재료가 모두 `ready` 또는 `existing`인지 확인한 뒤 새 배치를 등록합니다. 미완료면 초안·완료 이미지를 보존하고 원인을 보고합니다. 재료 승인·보류 결정은 대신하지 않습니다.
- 공통 절차대로 서버의 해당 배치와 현황 링크를 확인해 전달합니다. 재료는 사용자가 **신규 추가·대체·보류**를 먼저 결정하며, 미승인 재료를 쓰는 놀이는 초안으로 남깁니다. 대체로 바뀐 방법·주의사항·이미지는 다시 검수합니다.
- 파일 수정 후 서버 화면을 새로고침합니다. 오래된 화면의 승인이나 상태 파일을 복사해 변경된 내용에 적용하지 않습니다. 오프라인 JSON 흐름도 기존 도구의 배치·내용·이미지 검증을 거칩니다.

전체 흐름으로 임포트까지 진행했다면 실제 신규 ID, 배치 경로, 확인한 서버 검수·현황 링크도 함께 전달합니다. 정규화만 끝낸 항목을 등록 완료로 보고하지 않습니다.
