# 로컬 검수 서버

```bash
pnpm review:local
# http://127.0.0.1:4317/catalog
# 다른 포트: pnpm review:local --port 4320
```

기존 현황·검수 HTML 생성기를 메모리에서 실행합니다. 현재 JSON과 이미지를 읽으므로
화면을 여는 것만으로 마스터·검수 기록·HTML 파일을 변경하지 않습니다. 수집 스킬이나
CLI가 파일·배치를 추가한 뒤 **최신 파일로 새로고침**을 누르면 목록과 상세가 갱신됩니다.
다른 화면에서 변경이 발생하면 5초 간격 확인으로 갱신 안내를 표시합니다.

메뉴별 주소는 놀이 목록 `/catalog`, 재료 라이브러리 `/materials`, 수집 건별 검수 목록
`/reviews`이며, 개별 검수 주소는 `/reviews/<batchId>`입니다. 메뉴는 실제 페이지 링크로
이동하므로 직접 접속·새로고침·뒤로·앞으로 가기에서도 해당 화면을 엽니다. API 목록의
`url`은 개별 검수 주소입니다. `/`와 기존에 등록된 `.html` 주소는 새 주소로 이동하며
query와 놀이 ID hash를 유지합니다. 기존 `#materials`·`#review-batches` 북마크는 각각
`/materials`·`/reviews`로 이동합니다. 정적 파일의 실제 이름과 `file://`의 상대 링크는
기존대로 유지합니다.

검수 의견·확인란·상태는 입력 후 250ms에 서버 파일로 저장됩니다. 재시작과 다른
브라우저에서도 복원됩니다. 놀이 **승인**은 그 항목만 검증하여 로컬 마스터와 앱 이미지
매핑에 반영하고 화면을 갱신합니다. 재료 **신규 추가·대체·보류**도 선택한 재료만
반영합니다. 재료 대체 뒤에는 기존 규칙대로 방법·주의사항 수정과 재검수가 필요합니다.
JSON 가져오기는 기록만 저장합니다. 가져온 승인은 각 항목의 승인 버튼을 눌러 반영합니다.

`file://` HTML의 브라우저 저장, JSON 내보내기·가져오기와 기존 CLI 명령도 유지합니다.
파일로 열었던 검수 기록은 해당 화면에서 JSON을 내보내 서버 화면으로 가져오세요.
기존 브라우저 기록을 삭제하거나 자동으로 로컬 마스터에 반영하지 않습니다.
정적 HTML은 기존 `pnpm catalog:build`, `pnpm review:prepare --batch ...`로 갱신할 수 있습니다.

## 수집 스킬에서 검수로 넘기기

수집·정규화·임포트 스킬은 다음 절차를 공통으로 사용합니다. 명령은 저장소 루트에서
실행합니다. 수집 전체 흐름은 검수 가능한 서버 링크 전달까지 진행하며, 조사·정규화만
명시적으로 요청한 작업은 그 산출물까지 완료합니다.

1. 수집 원본을 보존하고 정규화 파일에 `meta.query`, `meta.activityReviews`,
   `meta.materialProposals`를 유지합니다. 임포트에는 이번 파일의 실제 경로를 명시합니다.
   신규 놀이는 `draft`·`imageStatus: review`, 신규 재료는 임시 정의와 `reviewPending`으로
   준비합니다. `_done` 파일명과 정규화·임포트 완료는 승인 표시가 아닙니다.
2. 실제 신규 ID를 [대표 이미지 생성 절차](IMAGE-WORKFLOW.md)에 연결합니다.
   `generate-play-images` 스킬이 프롬프트 작성부터 실제 `image_gen` 호출·시각 확인·
   `review:image` 저장까지 별도 요청 없이 수행합니다. `review:images`에서 모든 ID가
   `ready`가 되면 `generate-material-images` 스킬로 이번 놀이가 쓰는 새 재료의 이미지도
   확인합니다. 실제 기존 이미지는 재사용하고 없으면 `image_gen` 호출·시각 확인·
   `review:material-image` 저장·매핑을 수행합니다. `review:material-images --ids ...`에서
   모두 `ready` 또는 `existing`이 된 뒤 다음 단계로 진행합니다. 실패 시 초안과 완료한 이미지·프롬프트를
   보존하고 미완료 ID를 보고하며, 새 검수 배치를 먼저 만들지 않습니다.
3. 파일별 실제 신규 ID와 현재 존재하는 정규화 파일을 사용해
   `pnpm review:prepare --ids <실제-신규-ID목록> --source <정규화-파일> --title <수집-제목>`을
   실행합니다. `--source` 파일의 메타데이터가 재료 제안과 검토 근거로 연결됩니다.
   반환된 `batchPath`, `batchId`, `review`를 보존합니다. 신규 ID가 없으면 빈 배치를 만들지
   않고, 해당하는 기존 배치 또는 전체 현황을 안내합니다.
4. 같은 수집 건의 수정·이미지 추가는 `pnpm review:prepare --batch <기존-배치-경로>`로
   갱신합니다. 새로 등장한 재료의 제안은 해당 배치의 `materialProposals`에 필요한 만큼
   보완하되 `batchId`, 기존 대상, `appliedMaterialDecisions`,
   `entries.materialReplacementChecks`를 보존합니다. 배치를 통째로 새로 쓰거나 서버의
   `state.json`·거래·영수증을 직접 편집하지 않습니다. 자료를 쓸 때는 저장 직전 최신 파일을
   다시 읽고, 외부 변경이 있으면 ID·중복·매핑을 최신 상태에서 다시 계산합니다.
5. 이 저장소에서 실행한 서버가 있으면 재사용하고, 없으면 `pnpm review:local`을 실행합니다.
   기본 주소는 `http://127.0.0.1:4317`입니다. 다른 포트를 썼다면 실행 출력의 실제 주소를
   사용합니다. 해당 포트가 다른 서버에서 사용 중이면 그 프로세스를 종료하지 말고
   `--port`로 다른 loopback 포트를 선택합니다.
6. `GET /api/local-review/batches`의 목록에서 반환된 `batchId`를 찾고,
   `GET /api/local-review/batches/<batchId>`의 대상 ID·`manifest.batchHash`를 현재 로컬 파일의
   `scripts/review/review-core.mjs`의 `createManifest` 결과와 대조합니다. 이 GET 확인에는
   Node의 `fetch` 등 사용 가능한 읽기 도구를 사용할 수 있습니다. 목록의 `url`을 실제 서버
   주소와 조합하고 HTML 응답도 확인합니다. 과거 14개 검수 URL이나 추정한 배치 이름을
   새 수집 건 링크로 대신하지 않습니다.
7. **해당 수집 건의 서버 검수 URL과 전체 현황 URL**을 전달합니다. 현황 경로는
   `/catalog`입니다. 재료 목록은 `/materials`, 수집 건별 목록은 `/reviews`이며,
   해당 수집 건 경로는 목록 API가 반환한 `/reviews/<batchId>`를 사용합니다.
   실제 신규 ID·놀이 수, 신규 재료·미완료 이미지 수,
   미해결 사유와 배치 경로를 함께 안내합니다. 이미 열려 있던 화면은 **최신 파일로
   새로고침**하면 새 수집 건과 수정한 내용이 나타납니다. 서버가 실행되지 못했다면 그
   사유와 생성된 정적 HTML의 실제 경로를 전달하고, 서버 자동 저장·즉시 반영은 미연결로
   구분합니다.

검수 준비 중에는 사용자 확인란·승인 버튼을 대신 조작하거나 승인 JSON을 만들어 게시하지
않습니다. 사용자 승인이 이미 명시된 경우에는 그 범위와 현재 내용·이미지를 기존 도구로
검증하여 처리합니다. 서버 UI에서는 신규 재료를 먼저 결정하고, 본문·재료·대표 이미지를
확인한 놀이의 승인 버튼으로 해당 항목만 반영합니다. 재료 승인만으로 놀이가 게시되지
않으며, 보류·수정 요청·미검수는 초안을 유지합니다. 등록 완료 항목은 재승인을 요구하지
않습니다. 내용·이미지 변경 후에는 새로고침한 현재 화면에서 다시 검수합니다.

서버 UI 승인 뒤에는 JSON 내보내기나 CLI 적용을 다시 요구하지 않습니다. JSON 가져오기는
기록 저장이므로 승인 버튼으로 별도 반영합니다. 사용자가 `file://`·JSON/CLI 방식을 선택한
경우에는 같은 배치의 `review:materials` 미리보기·`--write` → 변경 후 화면 갱신·재검수 →
최신 `review:apply` 미리보기·`--write` 순서를 유지합니다. `409`는 최신 파일로 다시 검수하고,
`423`은 아래 복구 절차를 따릅니다. 버전 값만 바꿔 승인 요청을 재전송하지 않습니다.
로컬 반영은 공개 배포가 아니며, 커밋·푸시·배포는 별도 요청 범위입니다.

## Codex에 수집 건 검수 요청

개별 검수 화면의 **JSON 내보내기** 옆 **Codex에 검수 요청**을 누르면 입력 중인 의견부터
저장하고, 현재 수집 건 전체의 검수 결과·내용/이미지 해시·배치 경로를 묶어 **새 로컬
Codex 채팅을 만들어 요청**합니다. 제목은 `놀이 검수 · <수집 건 제목>`이며 현재 채팅과
대화 이력을 공유하지 않습니다. 화면의 검색·필터로 일부만 보여도 요청 범위는 현재
수집 건 전체입니다. 전송 후 표시되는 **새 채팅 열기** 링크에서 진행 결과를 확인하고,
수정한 항목은 같은 검수 화면에서 다시 확인하고 승인합니다.

[공식 Codex 앱 서버 프로토콜](https://learn.chatgpt.com/docs/app-server)의 `thread/start` →
`thread/name/set` → `turn/start`를 사용합니다. 저장소를 작업 폴더로 지정하고 사용자가
설정한 기본 모델을 사용하며 작업 파일 쓰기 범위를 workspace로 제한합니다. 별도 작업
프로세스가 완료까지 연결을 유지하므로 검수 서버 재시작이 해당 프로세스를 종료하지
않습니다. 추가 사용자 입력이나 권한 승인을 대신 허용하지 않습니다.

앱이 제공하는 `CODEX_CLI_PATH` 실행 파일을 우선 사용하고, 없으면 PATH의 `codex`를
사용합니다. 다른 실행 파일은 `NORI_CODEX_BIN`으로 지정할 수 있습니다. 기존 채팅 UUID나
`--codex-thread` 설정은 사용하지 않습니다. 브라우저가 임의의 채팅·프롬프트·명령을
지정할 수 없으며 새 채팅 ID는 Codex의 생성 응답에서만 받아 저장합니다.

요청 파일과 전달 상태는 `results/local-review/codex-requests/<hash>.json`에 보관합니다.
같은 수집 건의 동일한 내용·의견을 반복 클릭하면 이미 생성한 채팅 링크를 반환합니다.
내용이나 의견이 바뀐 다음 요청은 새 채팅으로 만듭니다. 생성 후 전송만 실패한 경우는
생성한 채팅 ID를 보존해 같은 채팅으로 재시도하고, 시간 초과 등으로 전달 여부가
불분명하면 중복 생성을 막으므로 먼저 Codex 채팅을 확인합니다. 이 파일은
서버의 공개 경로로 제공하지 않습니다. 정적 `file://` 화면에는 전송 버튼을 표시하지 않습니다.

전달 메시지는 구체적인 수정 요청이 있는 미등록 항목을 보완하고 같은 배치를 갱신하도록
지시합니다. 수정 요청이 없으면 검수 결과를 보고하며, 등록 완료·승인·보류 상태를 임의로
바꾸거나 자동 승인·등록·커밋·푸시·배포하지 않도록 명시합니다. 버튼 클릭 전에는 요청을
전송하지 않습니다. 자동화 테스트는 격리된 데이터와 가짜 Codex 프로토콜 프로세스로
실행하며 실제 수집 건의 검수 작업을 테스트로 시작하지 않습니다.

## 파일과 코드 위치

| 위치 | 내용 |
| --- | --- |
| `tools/local-review/server.mjs` | 루프백 HTTP 서버, 경로·요청 검증, HTML 연결 |
| `tools/local-review/service.mjs` | 검수 상태 복원, 저장 직렬화, 기존 승인 모듈 호출 |
| `tools/local-review/files.mjs` | 파일 버전, 원자적 교체, 거래 백업·복구 |
| `tools/local-review/browser.js` | 서버 자동 저장, 승인 연결, 갱신 안내 |
| `tools/local-review/codex-requests.mjs` | 수집 건별 검수 요청 보관, 새 채팅 생성 실행, 중복 방지 |
| `tools/local-review/codex-worker.mjs`, `codex-client.mjs` | 별도 작업 프로세스, Codex JSON-RPC 연결, 새 채팅 생성·요청·완료 기록 |
| `tools/local-review/tests/` | 격리된 데이터의 HTTP·저장·승인·복구 테스트 |
| `results/local-review/state.json` | 배치별 상태·의견·검수 당시 해시 |
| `results/local-review/transactions/<ID>/` | 변경 전후 파일과 `plan.json` 거래 기록 |
| `results/review-backups/`, `results/material-review-backups/` | 기존 승인 모듈의 백업과 영수증 |

런타임 저장은 기존 `results/` Git 제외 규칙을 따릅니다. `src/`, 공개 웹 서버,
앱 실행 경로에 관리 서버 코드를 넣지 않습니다. 공용 검수 코드에는 메모리 렌더링 옵션,
자동 저장 시 미완성 의견 허용 옵션, 선택적인 저장 연결만 추가했습니다. 핵심 승인·재료
제약·이미지 매핑·기존 이력 복원은 `scripts/review/`와 기존 반영 모듈을 호출합니다.

화면의 공통 사이드바·아이콘은 `scripts/review/backoffice-html.mjs`, 색상·타이포그래피·
반응형 레이아웃은 `scripts/review/backoffice.css`에서 관리합니다. 현황과 검수 화면의
개별 스타일은 같은 폴더의 `catalog.css`, `review.css`로 나눕니다. 스타일과 아이콘은
생성 HTML에 포함되어 `file://`에서도 외부 리소스 없이 동작합니다.

## 충돌과 복구

각 저장은 화면의 파일 버전을 전송합니다. 마스터, 배치, 이미지, 이미지 매핑, 영수증,
검수 저장 파일 중 하나라도 달라지면 오래된 요청은 `409`로 거부합니다. 같은 버전을
보낸 동시 요청 중 하나만 저장됩니다. 화면에서 실패를 표시하며, 현재 의견을 JSON으로
내보내 보관한 뒤 최신 화면을 열 수 있습니다. 내용·이미지가 바뀌면 확인란과 미반영
승인을 초기화하고 의견은 남깁니다. 이미 등록된 항목은 등록 완료로 표시합니다.

승인 모듈은 임시 사본에서 먼저 실행합니다. 검증된 파일만 원본의 버전을 다시 확인해
거래에 포함합니다. 원본 변경 전 변경 전후 파일과 거래 계획을 디스크에 동기화하고,
파일을 원자적으로 교체합니다. 실패 시 되돌리며, 중간에 외부 수정된 파일은 덮어쓰지
않습니다. 서버 프로세스 간에는 저장소별 잠금 파일을 OS 임시 폴더에서 사용합니다.
잠금을 공유하지 않는 외부 편집기도 반영 전후 파일 비교로 감지하지만, 승인 반영 중
같은 파일을 동시에 편집하는 작업은 피하는 편이 좋습니다.

프로세스 중단으로 `prepared` 거래가 남으면 읽기는 허용하고 쓰기는 `423`으로 막습니다.
화면에 표시된 거래 ID로 서버를 종료한 뒤 명시적으로 복구합니다.

```bash
pnpm review:local --recover <거래ID>
pnpm review:local
```

복구는 모든 대상이 변경 전 또는 해당 거래의 변경 후 해시인지 먼저 확인하고 변경 전으로
되돌립니다. 이후 외부 수정이 있으면 자동 복구를 거부합니다. 이 경우 `plan.json`의
경로·해시와 같은 폴더의 `<번호>.before` / `<번호>.after` 파일, 기존 승인 영수증을
비교하여 필요한 내용만 수동 복구하세요. `committed` 거래의 기록도 보관하므로 저장 파일
손상 시 마지막 정상 `state.json`에 해당하는 `.after` 사본을 확인할 수 있습니다.
서버는 손상된 저장 파일을 초기화하거나 과거 상태로 자동 덮어쓰지 않습니다.

## HTTP 범위와 검증

기본 바인딩은 `127.0.0.1`입니다. Host를 현재 포트의 `127.0.0.1`·`localhost`로
제한하고, 허용된 현황·검수 HTML, 이미지, 브라우저 연결 코드만 제공합니다. 마스터 JSON,
백업, 소스, 환경 파일, 임의 `results/` 파일은 공개하지 않습니다. 심볼릭 링크와 경로
이탈도 거부합니다. 쓰기는 같은 origin, 서버 세션 토큰, JSON 형식, 2MiB 한도,
배치·항목·해시·기존 검수 규칙을 검증합니다. 재시작하면 화면을 다시 열어야 합니다.

| API | 용도 |
| --- | --- |
| `GET /api/local-review/batches` | 수집 건 목록과 현재 버전 |
| `GET /api/local-review/batches/<batchId>` | 현재 manifest와 복원한 기록 |
| `GET /api/local-review/version` | 외부 변경·미완료 거래 확인 |
| `POST /api/local-review/batches/<batchId>/save` | 상태·의견 저장, 승인 반영 없음 |
| `POST /api/local-review/batches/<batchId>/approve` | `id` 놀이 한 개 승인 반영 |
| `POST /api/local-review/batches/<batchId>/materials` | `id` 재료 한 개 결정 반영 |
| `POST /api/local-review/batches/<batchId>/codex-request` | 현재 `revision`의 수집 건 검수 결과를 새 채팅으로 전달하고 `threadId`·`threadUrl` 반환 |

POST 본문은 `{ revision, results, id? }`, 토큰 헤더는 `X-Nori-Review-Token`입니다.
서버 시작·GET·JSON 가져오기는 승인 동작이 아닙니다. 커밋·푸시·빌드·배포는 실행하지 않습니다.

```bash
pnpm test:local-review
pnpm test:play-review
pnpm check:play-content
pnpm typecheck
```

HTTP 테스트는 임의 loopback 포트를 사용합니다. 포트 바인딩이 제한된 샌드박스에서는
로컬 포트 사용 권한이 필요합니다. 쓰기·승인 테스트는 OS 임시 폴더의 fixture만 사용합니다.
