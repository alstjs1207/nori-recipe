# 찜한 놀이 분류 설계안

## Context

현재 favorites는 guestId와 playId별 고유 찜을 저장하며 활성 조회와 tombstone 전환을 제공한다. 웹은 AsyncStorage, 네이티브는 SQLite다. 모음과 분류 데이터는 없고 두 플랫폼의 찜 화면은 각각 구현되어 있다.

## Goals / Non-Goals

- 목표: LOG-004·LOC-004를 제공하면서 기존 찜 API·찜 개수·완료 기록의 의미를 보존한다.
- 제외: 서버 공유·계정 기능, 다중 모음 배정, 일정·알림, 모음별 추천 가중치.

## Decisions

1. **모음과 찜은 별도 개념**: 모음에는 ID·guestId·이름·생성/수정 시각·삭제 정보를 두고 찜에는 nullable 모음 참조를 추가하는 안을 사용한다. 찜 자체를 복제하는 방식은 전체 개수·해제 처리를 복잡하게 하므로 채택하지 않는다.
2. **단일 분류 첫 버전**: 찜 하나에 모음 최대 하나를 연결한다. 전체·미분류는 저장 모음이 아닌 화면 분류다. 새 모음을 강제로 생성하거나 기존 찜을 임의의 모음으로 나누지 않는다. 모음 이름은 trim 후 1~20자이며 동일 게스트 내 같은 이름과 전체·미분류 이름을 거부한다.
3. **삭제 의미 분리**: 모음 삭제 시 소속 활성 찜은 미분류로 이동한다. 찜 해제는 기존 tombstone을 유지하고 재찜 시 분류를 비운다. 전체 목록은 모음과 관계없이 고유 찜을 한 번씩 표시한다.
4. **관계 변경 일관성**: 네이티브는 트랜잭션으로 모음 삭제·참조 정리를 처리한다. 웹은 변경 전 snapshot·직렬화·실패 복구를 사용해 일부 쓰기만 반영된 고아 관계를 방지한다. 유효하지 않은 참조는 다른 사용자의 모음으로 연결하지 않고 미분류로 읽는다.
5. **분류 UI**: 찜 화면에 분류 선택과 모음 관리, 카드에 이동/분류 해제를 제공한다. 상세·검색의 기존 찜 버튼은 분류 선택 없이 사용할 수 있다. 기본 이름 예시는 안내에만 사용한다.
6. **개인 입력 보호**: 모음 이름·모음 ID·분류 정보는 분석 이벤트와 공유 URL에 넣지 않는다. 기존 `favorite_add/remove`의 공개 놀이 ID 기반 동작만 유지하고 공통 로컬 저장 안내에 분류를 반영한다.

## Risks / Trade-offs

- [모음 삭제가 찜 삭제로 오인됨] → 확인 문구와 미분류 이동 결과를 명시한다.
- [마이그레이션으로 기존 찜 유실/부활] → 활성·삭제 표시 찜을 혼합한 fixture로 ID·시각·tombstone 보존을 검증한다.
- [재실행 후 고아 참조·다중 탭 덮어쓰기] → 저장 실패·경합·부분 쓰기 복구 회귀를 추가한다.

## Migration Plan

- 네이티브는 추가 migration으로 nullable 분류와 모음을 도입하고, 웹은 누락 분류를 미분류로 읽는다. 기존 찜을 다시 생성하거나 사용자 데이터를 초기화하지 않는다.
- `add-recently-viewed-plays`와 migration 순번을 공유 확정하지 않는다. 실제 반영 순서에 맞게 순차 이관하고 두 변경의 조합도 검증한다.
- 활동 초기화에 모음·분류의 삭제 처리를 연결하고 전체 삭제에 해당 게스트의 모음 데이터도 포함한다. 로그·찜의 기존 삭제 표시 계약은 유지한다.
- 실패 시 기존 찜을 표시할 수 있도록 읽기 호환을 유지한다. rollback은 분류 UI/쓰기를 중단하는 방식이며 기존 테이블·DB 버전을 강제로 되돌리지 않는다.
- 후속 구현에서 현재 명세·policy-map·필요한 source-index를 갱신한다. 콘텐츠·이미지·승인 해시는 건드리지 않고 웹 Preview·네이티브 검증과 실제 배포는 별도로 기록한다.
