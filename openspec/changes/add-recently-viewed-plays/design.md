# 최근 본 놀이 설계안

## Context

목적과 제안 범위는 proposal.md를 따른다. 현재 `getPlayLogs`는 완료 기록이며 열람 이력이 아니다. 상세는 웹·네이티브로 나뉘고 사용자 데이터는 SQLite/AsyncStorage에 저장한다. 게스트별 열람 목록 모델은 없다.

## Goals / Non-Goals

- 목표: CAT-005·LOC-003을 플랫폼 간 동일하게 제공하고 기존 활동 데이터를 보존한다.
- 제외: 완료 로그 전용 화면 재사용, 열람 기반 추천 가중치 변경, 서버 저장, 추가 분석 전송.

## Decisions

1. **별도 열람 저장소**: `(guestId, playId, lastViewedAt)`을 저장하고 게스트·놀이별로 upsert한다. 완료 로그 재사용은 열람이 완료 경험으로 섞이므로 채택하지 않는다. 최신 20개만 남기는 제한은 저장 시 적용한다.
2. **상세가 실제 활성화될 때 기록**: 웹/네이티브의 상세 focus와 공개 놀이 확인 후 기록한다. 프리렌더·정적 HTML 생성·이미지 요청·카드 노출은 열람으로 처리하지 않는다. 중복 effect 호출에도 항목이 늘지 않도록 한다.
3. **탐색 화면에서 재발견**: 검색어·필터를 적용하기 전 최근 본 영역과 비우기를 제안한다. 일반 검색 결과와 구분하고 기존 검색 필터·정렬 동작을 바꾸지 않는다. 노출 위치의 구체 레이아웃은 구현 때 검토한다.
4. **재조회 때 공개 목록과 결합**: 삭제·비공개 항목은 표시에서 제외한다. 상세로 다시 이동해도 필수 준비·안전 안내를 그대로 제공한다.
5. **초기화 통합**: 열람 목록 비우기는 열람 저장소만 정리한다. `resetUserActivity`, `deleteAllUserData`, `resetLocalData`에는 해당 게스트 열람 데이터 정리를 포함한다. 분석 동의와 별개의 사용자용 로컬 기능이며 공통 저장 안내 문구에 이를 반영한다.

## Risks / Trade-offs

- [열람 쓰기 실패로 상세 진입이 막힘] → 저장은 상세 표시를 막지 않는 부가 작업으로 분리하고 실패 안내·복구를 검증한다.
- [여러 화면/탭 쓰기가 서로 덮어씀] → 네이티브 트랜잭션과 웹 쓰기 직렬화·최신 읽기 병합을 검토하고 동시 쓰기 fixture를 추가한다.
- [정렬 동률·손상값] → 저장 시각 검증과 안정적 정렬, 유효한 항목만 보존하는 복구를 적용한다.

## Migration Plan

- 기존 데이터를 초기화하지 않고 네이티브에 추가 migration, 웹에 게스트 분리 저장을 추가한다. 기존 사용자는 빈 열람 목록으로 시작한다.
- `add-favorite-collections`와 동일 DB 버전 번호를 미리 확정하지 않는다. 먼저 반영된 migration 다음 버전으로 순차 이관하고 두 적용 순서를 검증한다.
- 후속 구현에서 타입·명세·policy-map·필요한 source-index를 갱신한다. 콘텐츠·이미지·승인 해시는 변경하지 않는다.
- 실패 시 이전 활동 저장을 유지하고 새 기능 노출을 중단한다. DB 버전 강제 하향이나 기존 테이블 삭제로 복구하지 않는다.
- 검증은 fixture/임시 저장소에서 수행한다. 웹 Preview 및 네이티브 확인 증거와 실제 배포 여부는 별도로 기록한다.
