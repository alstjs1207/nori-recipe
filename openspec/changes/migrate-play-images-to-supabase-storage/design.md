# 놀이 이미지 Storage 이관 설계 — 예정·미착수

## Context

동기는 [proposal.md](proposal.md)를 따른다. 원본 프로젝트 `/Users/msyu/study/play-recipe`에서 2026-11-14 읽기 확인한 현재 구조는 다음과 같다.

- `images/plays/`의 JPEG 224개가 Git 추적 대상이다. 이 숫자는 조사 시점의 수량이며 이관 도구의 고정 기대값으로 사용하지 않는다.
- `prepare-web-assets.mjs`는 live 놀이의 로컬 JPEG에서 상세 960px 이내 WebP·썸네일 320px WebP를 생성한다. `imageStatus: review`는 기본 이미지로 처리한다.
- 웹 `playImageUrls.ts`와 공유 메타데이터 `scripts/web/html.mjs`는 `/media/plays/`를 각각 구성한다. 네이티브 `playImages.ts`는 원본 JPEG를 정적 require한다.
- 서비스 워커는 같은 origin만 처리하고 방문 미디어를 최대 80개 캐시한다. Storage URL만 바꾸면 원격 이미지가 이 캐시에서 빠진다.
- 검수·승인은 로컬 원본과 내용 해시에 의존한다. CI/Vercel 빌드도 저장소의 원본 파일을 전제로 한다.

## Goals / Non-Goals

**Goals:** CON-004·CON-005·WEB-003의 제안 계약을 만족하고 기존 원본·검수 승인·게스트 데이터를 보존한다. 새 checkout과 자산 복원, 웹/PWA·공유·네이티브 소비 경로까지 재현 가능하게 전환한다.

**Non-Goals:** 콘텐츠 DB·사용자 계정·동기화는 별도 change다. 다른 종류 이미지 이관, 워터마크, Git 이력 재작성과 운영 배포는 이 계획 등록에 포함하지 않는다. 현재 명세와 policy-map에 미래 기능을 완료 근거로 추가하지 않는다.

## Decisions

### 1. 한 프로젝트에서 원본과 공개 자산을 분리

놀이 레시피 전용 Supabase 프로젝트 하나에 비공개 원본 버킷과 공개 서비스 자산 버킷을 둔다. 이름·리전·Preview/Production의 실제 연결은 착수 때 확인할 배포 설정이다. Free 조직의 프로젝트 한도와 실제 파일 총량을 확인하며 이 문서에서 요금이나 무료 유지 기간을 확정하지 않는다.

모든 쓰기는 로컬 관리 도구 또는 신뢰할 수 있는 관리 실행 환경에서만 수행한다. 공개 앱과 일반 Preview 빌드에는 원본 다운로드·업로드 자격 증명을 주지 않는다. 브라우저에서 원본을 변환하는 방식은 원본을 노출하므로 사용하지 않는다. 관리 작업에 필요한 SDK/CLI는 구현 때 결정하며 공개 이미지 조회를 위해 Auth를 추가하지 않는다.

### 2. 원본 해시와 파생 이미지 버전을 연결

Git에는 ID별 원본 체크섬·상세/썸네일 체크섬·공개 객체 경로·버전을 담은 매니페스트를 둔다. 공개 소비용 데이터에는 비공개 버킷 경로·서명 URL·비밀을 넣지 않는다. 비공개 복원에 필요한 매핑은 관리 도구의 입력으로 분리한다.

객체 경로는 `<playId>/<content-version>/detail.webp`, `thumbnail.webp`처럼 불변 버전을 사용한다. 현재 `?v=`만 바꿔 같은 Storage 객체를 덮어쓰는 방식은 CDN과 오래된 앱의 이미지가 뒤섞일 수 있어 채택하지 않는다. 원본 체크섬은 기존 검수 해시와 동일한 바이트를 기준으로 유지하고, 파생 변환 결과의 해시는 별도 검증한다. 최초 이관에서는 기존 변환 규격을 유지한다.

### 3. 공개는 검수 승인 뒤에만 연결

원본 준비·비공개 업로드와 공개 게시를 구분한다. 초안·검토 중 이미지도 관리자가 비공개 보관할 수 있지만 공개 버킷 게시와 매니페스트 활성화는 승인된 live 이미지에 한한다. 업로드 자체로 로컬 JSON의 status나 승인 상태를 바꾸지 않는다.

기존 원본 해시가 같은 위치 이관은 재승인을 요구하지 않는다. 원본 변경은 기존 CON-003에 따라 재검수한다. 비공개 전환된 이미지는 현재 참조에서 즉시 제외하고 원격 공개 객체도 정리 대상으로 기록한다. 오래된 버전 정리는 배포·롤백에 필요한 참조를 확인한 뒤 별도 실행하며, 캐시·기존 다운로드 회수는 보장하지 않는다.

### 4. 웹은 공개 URL, 네이티브는 서비스 자산 번들

웹 화면과 공유 HTML은 동일 매니페스트의 공개 URL을 사용하고 origin 치환이 Storage URL을 서비스 도메인으로 잘못 바꾸지 않도록 한다. 공유 봇에는 인증·만료 URL을 요구하지 않는다. 재료·환영·브랜드 자산의 기존 생성 경로는 유지한다.

PWA는 명시적으로 허용한 Storage origin 및 공개 버킷 경로의 이미지만 캐시 대상으로 추가한다. 읽을 수 있는 응답이 캐시되도록 CORS와 이미지 요청 모드를 맞추고, opaque 응답·오류 응답을 정상 캐시로 취급하지 않는다. 버전별 캐시, 80개 상한, 선택 업데이트는 유지한다. 이미지 실패 시 기본 표시를 제공하고 본문·찜·기록은 계속 사용할 수 있게 한다.

네이티브는 공개 서비스용 이미지를 빌드 전에 체크섬 검증해 Git에서 제외된 생성 디렉터리에 준비하고 정적 참조를 생성한다. 원본 번들을 제거하면서 기존 오프라인 이용을 보존하려는 선택이다. 원격 URL만 참조하는 대안은 첫 오프라인 실행의 표시를 바꾸므로 채택하지 않는다. 외부 자산이 필요한 빌드는 검증된 로컬 캐시로 재시도할 수 있으며 필수 이미지가 없으면 실패한다. 테스트는 원격 서비스 없이 fixture로 실행할 수 있게 한다.

### 5. 로컬 검수·신규 이미지 작업 유지

`images/plays/`는 관리자가 복원하거나 새 이미지를 생성하는 로컬 검수 경로로 유지한다. 기존 `review:image`·이미지 검사·로컬 검수 UI의 파일 및 해시 계약을 보존한다. 복원은 임시 파일에 다운로드·해시 검사 후 배치하고 기존의 다른 바이트 파일을 조용히 덮어쓰지 않는다. 공개 배포 빌드는 이 비공개 원본 복원 단계를 요구하지 않도록 분리한다.

## Risks / Trade-offs

- 공개 이미지 다운로드·과거 Git 원본 접근 → 원본 보호의 적용 경계를 문서화한다. 과거 이력 제거는 별도 요청 대상이다.
- Storage 장애·무료 한도·전송량 → 자산 크기·전송량을 확인하고 버전별 캐시·재시도·기본 표시를 제공한다. 장애를 해결하려고 원본을 공개하지 않는다.
- 서로 다른 원본/파생 버전 → 원본과 파생 체크섬을 연결하고 업로드 검증 전에 매니페스트를 전환하지 않는다.
- 로컬 검수와 배포가 서로 다른 자산 사용 → 동일 ID·원본 해시 기반 매니페스트와 회귀로 대조한다.
- Git 파일을 먼저 제거해 복원·빌드 불가 → 원격 다운로드 복원 및 새 checkout 빌드 검증을 추적 제외의 선행 조건으로 둔다.
- 새 이미지 origin의 외부 요청 → 개인정보 고지의 자산 제공처·로그 설명을 점검한다. GA4 동의 버전·분석 이벤트는 임의 변경하지 않는다.

## Migration Plan

1. 실제 실행 요청 시 대상 프로젝트·환경·버킷·접근 권한을 정하고 ID별 전체 파일 목록과 해시를 기록한다. live·review·draft·archived를 구분하고 기존 고유 파일을 보존한다.
2. 원본 비공개 업로드·권한 검사·다운로드 체크섬을 확인한 뒤 승인된 서비스용 이미지와 버전 매니페스트를 준비한다. 부분 성공은 기록해 재개한다.
3. 새 URL·공유 메타데이터·PWA 캐시·네이티브 생성 자산을 연결하고 검수·생성 흐름을 검증한다. 기존 ID·찜·기록·GA4는 바꾸지 않는다.
4. 새 checkout에서 원본 복원과 공개 자산만을 사용하는 배포용 빌드를 각각 검증한다. 업로드·복원·모든 소비 경로 검증이 끝난 대상만 로컬 파일을 유지한 채 Git 추적에서 제외한다.
5. 실제 구현과 현재 명세·policy-map·source-index·운영 문서를 함께 갱신한다. 로컬 검증과 실환경 확인 결과를 구분해 남기고 preview→main 배포는 그때의 요청 범위를 따른다.

롤백은 마지막 정상 매니페스트·공개 객체 버전으로 되돌린다. 원본과 직전 서비스 버전은 전환 검증 중 삭제하지 않으며, 필요 시 권한 있는 원본 복원으로 이전 빌드를 재현한다. 사용자 로컬 저장소 초기화나 원본 버킷 공개를 복구 수단으로 삼지 않는다.

## Open Questions

- 착수 시 사용할 Supabase 프로젝트 참조·버킷 이름·리전과 환경별 공개 자산 주소를 확정한다. 이 값들은 계약과 작업 분해를 바꾸지 않는 배포 설정이다.
